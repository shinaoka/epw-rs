# AI 開発の時代に OpenMX を次の世代へ：モジュール化，Rust crate 化，ライセンスについての相談

**対象：OpenMX 開発者の皆様**

**作成：品岡 寛（埼玉大学），tensor4all**

> 本資料は議論のたたき台であり，決定事項や公式の開発計画ではありません．ライセンスに関する記述は，GNU プロジェクトの公式 FAQ などの一次情報をもとに筆者がまとめた理解であり，法的助言ではありません．出典は末尾にまとめています．

> 関連資料（英語）：[Why Rewrite First-Principles Codes in Rust](why_rusty_openmx.md)，[OpenMX Code Analysis](openmx_analysis.md)

## 要旨

1. **AI エージェントによる開発が標準になりつつあります．** AI はコードを書くだけでなく，コンパイルし，テストを実行し，結果を見て自分で直すところまでを自動で繰り返します．これが機能するのは，**部品ごとに数秒で正しさを確かめられるコード**（モジュール化とユニットテスト）だけです．本資料では，この「変更のたびにその場で AI が正しさを確認する」仕組みを「AI によるファーストフィードバック」と呼びます．
2. **AI で開発を加速できないコードには，新しい開発者が参入しなくなります．** 学生や若手，他分野の研究者は，同じ時間で成果の出るコードを選ぶからです．OpenMX の優れた物理を次の世代に引き継ぐには，AI で加速できる構造が条件になると考えています．
3. **AI で加速するための条件は，大域変数をやめて部品に分け，部品ごとにテストを付けることです．** 「大域変数で書くから速い」は多くの場合事実ではなく，速度（メモリ配置，ノード間のデータ配置など）は大域変数なしで最適化できます．大域変数の本当の問題は，独立したユニットテストが書けないことです．
4. **Rust は，この構造を作り，守り，外に届けるのに適しています．** コードを **crate**（独立にビルド・テスト・配布できる部品）に分けられ，境界はコンパイラが守らせます．一つのワークスペースで開発しても，利用者は `cargo add openmx-basis` の 1 行で必要な部品だけを使えます．MPI，HDF5，CUDA は実行時に読み込めるためビルドが簡単で，線形代数やテンソルの並べ替えなど他で開発された高性能なライブラリも取り込めます．ただし，**同じ構造のまま移植しても意味はありません**．
5. **部品に分けると，部品そのものが外で使われるようになります．** phonopy（BSD）や libxc（MPL-2.0）が成功例です．OpenMX でも，例えば擬原子軌道（PAO）基底をライブラリにすれば，現在 OpenMX を改造して使っている機械学習ハミルトニアンのプロジェクトなどが，関数を呼ぶだけで済むようになります．
6. **ただし，元のコードが GPL だと，そこから作った部品も GPL を引き継ぎ，再利用の効果がほとんど失われます．** これを解決できるのは，**著作権者である OpenMX 開発者の皆様だけ**です．OpenMX 本体は GPL のまま，部品を別のライセンスでも公開する，という両立が可能です．ご意見を伺えれば幸いです．

## 1. AI 開発が標準になる：「ファーストフィードバック」とは

AI でのプログラミングを本格的に使ったことがない方には，具体的なイメージが湧きにくいかもしれません．まず，現在の AI 開発がどのようなものかを説明します．

### 現在の AI エージェントは何をするか

Claude Code などの AI エージェントは，チャットで質問に答えるだけではありません．**ファイルを編集し，コンパイルし，テストを実行し，結果を読んで自分で修正する**ところまでを自動で繰り返します．人間は「何をしたいか」を伝え，最後に結果を確認します．

### ユニットテストがある場合

例えば，PAO 基底の部品（`openmx-basis`）にユニットテストが揃っているとして，研究者が次のように頼んだとします．

> 「2 中心積分の計算を GPU で動くようにして．」

AI エージェントは次のように動きます．

1. `openmx-basis` の該当部分を書き換える
2. その部品のテストを実行する（**数秒**）
3. テストが失敗する．「l=2 の軌道で，ある原子間距離の重なり積分が，正解 1.2345×10⁻³ に対して 1.2401×10⁻³」
4. AI が原因を調べる．「GPU 版で球面調和関数の位相の規約が抜けている」と特定し，修正する
5. 再びテストを実行し，すべて通ることを確認する
6. 研究者に「GPU 化しました．全テスト通過，CPU 版との差は 10⁻¹⁴ 以下です」と報告する

この 2〜5 の繰り返しが，人間が見ていない間に数分で何十回も回ります．**変更のたびに，その場で正しさが確認される**．これがファーストフィードバックです．

### ユニットテストがない場合

同じ依頼でも，正しさを確かめる手段が「全系の SCF 計算を流して，全エネルギーが合うか見る」しかないと，

- 1 回の確認に数十分から数時間かかる
- 合わなかったときに，**どこが原因か分からない**（2 中心積分か，グリッドか，混合か……）
- AI は推測で修正するしかなく，誤った修正を重ねがちになる

結果として，AI に任せることも，人間が安心して変更することも難しくなります．

### まとめ

| | ユニットテストあり | ユニットテストなし |
|---|---|---|
| 1 回の確認にかかる時間 | 数秒 | 数十分〜数時間 |
| 間違いの場所 | 部品と入力まで特定できる | 分からない |
| AI に任せられるか | 修正と確認を自分で繰り返せる | 推測に頼るしかない |
| 機能追加・高速化 | 気軽にできる | 壊れるのが怖くて手を出しにくい |

私たちは tenferro-rs，tensor4all-rs などの Rust 数値計算ライブラリを，実際にこのやり方で開発しています．

### これからの開発者は「AI で加速できるコード」を選ぶ

率直に書くと，これが筆者の最も強い実感であり，本資料の出発点です．

AI を使った開発は，すでに一部の研究者にとっては日常になっており，今後は標準になっていくと考えられます．テストの整ったコードでは，機能の追加や高速化が人間だけで行うより何倍も速く進みます．逆に，AI で開発を加速できないコードでは，その恩恵をまったく受けられません．

そうなると，**新しく参入する人（学生，若手研究者，他分野の研究者）は，AI で開発を加速できるコードを選ぶ**ようになります．同じ時間をかけるなら，成果の出やすい方を選ぶのは自然なことです．大域変数で全体がつながり，全系を流さないと正しさを確かめられないコードは，どれほど物理が優れていても，**参入する気が起きにくい**コードになってしまいます．

これは，開発者の高齢化や後継者不足という，多くの第一原理計算コードが直面している問題と直結します．OpenMX の優れた物理と数値手法を次の世代に引き継ぐためにも，**AI で開発を加速できる構造にしておくことが，新しい開発者を呼び込む条件**になると考えています．

## 2. AI で加速するための条件：モジュール化とユニットテスト

### 必要なのは二つだけ

- **モジュール化：** 各部品は，受け取るデータと返すデータを引数と戻り値で明示し，大域状態を持たない
- **ユニットテスト：** 部品ごとに「この入力に対してはこの出力になるはず」という検証を用意する

関数が必要なものをすべて引数で受け取る形にしておけば，テストは「入力を作って，関数を呼んで，出力を比べる」だけになります．**モジュール化とユニットテストは「きれいなコードのため」ではなく，AI に安心して開発を任せるための前提条件**です．

### 第一原理計算はテストを作りやすい

第一原理計算は，同じ入力から同じ出力が得られる（乱数を使わない）計算です．そのため，**元の OpenMX に中間データを出力させて正解データとし，新しい部品の出力と数値を突き合わせる**テストを作りやすい，という大きな利点があります．正解データを作るためのコードの追加も，AI で自動化できます．

### 大域変数の本当の問題は，ユニットテストが書けないこと

- ある関数一つをテストしたくても，その関数が暗黙に読む大域変数を，すべて正しい状態に設定しなければなりません．どれを読んでいるかは関数の引数からは分からず，結局プログラム全体を初期化することになります
- テスト同士が同じ大域変数を共有するため，あるテストの結果が別のテストに影響したり，テストを並列に走らせられなかったりします
- その結果，「全系の計算を流して最後の数値を見る」以外の検証手段がなくなり，ファーストフィードバックが働かなくなります

### 大域変数をやめると遅くなるのでは？

「大域変数で書くから速い」と言われることがありますが，これは多くの場合事実ではありません．**大域変数を使わなくても，同じ速度を出すことは可能です．**

- **速度を決めるのは，メモリ配置，キャッシュの使い方，BLAS/LAPACK などの最適化されたライブラリの利用，計算の中心部でメモリ確保を繰り返さないこと**などです．データが大域変数にあるか引数で渡されるかは，本質ではありません
- 大規模並列計算では，**ノード間のデータ配置**（どの原子・行列ブロック・グリッド点をどの MPI プロセスが持つか，通信をどう減らすか）も速度を大きく左右します．これも大域変数とは無関係に最適化できます．むしろ，「分散配置の情報」を一つの型（構造体）にまとめて引数で渡すと，どの関数がどの配置を前提にしているかが明確になり，配置の方式を差し替えて比較することも容易になります
- 大きな配列を引数で渡しても，渡されるのは場所（ポインタ，参照）だけで，コピーは起きません．小さな関数はコンパイラがインライン展開するので，呼び出しのコストも通常は消えます
- 作業用の配列を毎回確保したくない場合は，それを構造体にまとめて一度だけ確保し，引数で渡せば同じ効果が得られます
- むしろ大域変数は，**どの関数がいつ書き換えるかコンパイラに分からない**ため，値をレジスタに置いたままにできないなど，最適化を妨げることがあります．Rust の参照は「この配列は他から同時に書き換えられない」ことを型で保証するので，コンパイラはより積極的に最適化できます

そして，テストが揃っていれば，**高速化そのものも AI に任せられます**．最適化のたびに正しさがその場で確認されるので，大胆な最適化を試しやすくなります．

## 3. 現状：第一原理計算コードは AI で加速しにくい

### OpenMX の構造

現在の OpenMX は，2 節の条件を満たしていません（詳細は [OpenMX Code Analysis](openmx_analysis.md)）．

- 全ソースファイルが `openmx_common.h` を読み込み，330 を超える大域変数を共有している
- 関数の引数を見ても，その関数が何に依存し，何を書き換えるのかが分からない
- 一つの実行ファイルとして動かす前提で，部分だけを取り出してビルド・テストする仕組みがない

これは OpenMX 固有の問題ではなく，数十年かけて発展してきた大規模な第一原理計算コードに共通する状況です．物理は優れていても，ソフトウェアの構造は書かれた時代を反映しています．

### 同じ構造は，外から部品として使えないことも意味する

AI で加速しにくい構造は，**部品を外から関数として呼び出せない構造**でもあります．OpenMX には，それ自体で価値のある部品がたくさんあります．

- 擬原子局在基底（PAO）とその動径関数の取り扱い
- 2 中心積分，Gaunt 係数，球面調和関数まわりの規約
- 実空間グリッド上の数値積分，Poisson 方程式の解法
- O(N) 法，NEGF による輸送計算，Wannier 関数の生成

これらは，機械学習ポテンシャル，タイトバインディング模型，DMFT，テンソルネットワークなど，他の研究コミュニティにとっても有用です．しかし現状では，次のようなことが起きています．

### 実際に起きていること：OpenMX を「改造して」使っている

OpenMX のハミルトニアンは，機械学習で DFT ハミルトニアンを予測する研究で学習データとして使われています．

- **DeepH-pack** は，データセット作成に OpenMX 3.9 のインストールを求めています（[README](https://github.com/mzjb/DeepH-pack)）．
- **HamGNN** は，`openmx_postprocess` という「**OpenMX を改造したプログラム**」を使って重なり行列や非自己無撞着ハミルトニアンを取り出しています．利用者は GSL，Intel MKL，Intel コンパイラのパスを Makefile に手で書いてビルドする必要があります（[README](https://github.com/QuantumLab-ZY/HamGNN)）．

改造版は OpenMX 本体の改良に追従しにくく，バグ修正も還元されにくいという問題もあります．

## 4. なぜ Rust か

### 同じ構造のまま移植しても意味がない

最初に強調しておきます．Rust に書き換えても，**大域変数を共有する一枚岩の構造をそのまま持ち込んでは意味がありません．** 部分だけを検証できないこと，部品として使えないことは何も変わらないからです．Rust 化の目的は，2 節の構造（モジュール化とユニットテスト）を作り，それを守り続けることです．

### AI が書き，コンパイラが検査する

Rust は，AI 開発と特に相性のよい言語です．

- **型と所有権の規則をコンパイラが厳しく検査する**ため，AI が書いたコードの誤り（メモリの不正利用，データ競合，型の取り違えなど）の多くが，実行する前にコンパイルエラーとして見つかります．AI はそのエラーを読んで自分で直します．ユニットテストと並んで，もう一段のファーストフィードバックになります
- **テストの仕組みが言語とツールに組み込まれている**（`cargo test`）ため，部品ごとのテストを書き，走らせるのが標準の作業になります
- 開発者が Rust を一から習得していなくても，AI が書いたコードをコンパイラとテストが検査するので，物理と数値の正しさに集中してレビューできます

### 部品の境界をコンパイラが守らせる

- 公開した関数以外は外から触れず，crate 間の循環依存も禁止されます．**大域変数で全体がつながった構造には戻れません**
- そのため，AI が機能追加を繰り返しても，「いつの間にか部品同士が絡み合ってテストが書けなくなる」ことが起きにくくなります．「基底の crate が SCF の crate に依存してしまい，基底だけ使うつもりが全部入ってくる」といったことも防げます

### crate とは：外から独立に依存して使える部品

Rust のプロジェクトは，複数の crate（部品）を組み合わせて作ります．一つのリポジトリの中に，次のように複数の crate を「ワークスペース」としてまとめて開発できます（どこに境界を引くかこそが，物理を理解している方々と相談したい最重要の設計判断です）．

```
openmx-rs/               # 一つのリポジトリ（ワークスペース）
├── openmx-basis/        # PAO 基底，擬ポテンシャル，2 中心積分
├── openmx-grid/         # 実空間グリッド
├── openmx-xc/           # 交換相関
├── openmx-poisson/      # Poisson ソルバー
├── openmx-hamiltonian/  # ハミルトニアン構築
├── openmx-eigen/        # 固有値問題
├── openmx-scf/          # SCF ループ
├── openmx-transport/    # NEGF
└── openmx-io/           # 入出力（OpenMX 形式互換）
```

各 crate は独立にビルド・テストできるので，AI は変更した crate のテストだけを数秒で回せます．そして，**開発は一つのワークスペースでまとめて行っても，利用者は必要最小限の crate だけを使えます**．

- 各 crate は，Rust の公式パッケージ登録サイト [crates.io](https://crates.io/) に**個別に公開**できます
- 例えば機械学習ハミルトニアンの研究者が PAO 基底だけを使いたい場合，自分のプロジェクトで次の 1 行を実行するだけです

```
cargo add openmx-basis
```

- すると `openmx-basis` と，それが依存するものだけが自動でダウンロード・ビルドされます．**SCF ループ，NEGF，MPI など，使わない部分は一切入ってきません**
- 利用者のコードからは，普通の関数として呼び出せます（以下はイメージです）

```rust
use openmx_basis::{PaoBasis, overlap_two_center};

let basis = PaoBasis::from_files("C6.0.pao", "C_PBE19.vps")?;
let s = overlap_two_center(&basis, orbital_a, &basis, orbital_b, r_ab);
```

- バージョン管理も crates.io が担います．利用者は `openmx-basis = "1.2"` のように使うバージョンを指定でき，OpenMX 側が改良版を公開すれば，利用者は 1 コマンドで更新できます

3 節で紹介した HamGNN の現状（OpenMX を改造したプログラムを，Makefile に MKL やコンパイラのパスを手で書いてビルドする）と比べると，違いは明らかです．**「OpenMX を改造して取り出す」から「OpenMX の部品を `cargo add` して呼ぶ」へ**．

### ビルドが簡単になる

第一原理計算コードを新しい計算機で動かすとき，最大の障害の一つはビルドです．OpenMX も，MPI，BLAS/LAPACK，ScaLAPACK，FFTW，ELPA などのパスを Makefile に手で書く必要があり，配布される Makefile にはスーパーコンピュータごとの設定がコメントとして並んでいます（[OpenMX Code Analysis](openmx_analysis.md)）．ビルドが難しいことは，AI にとっても障害です．環境ごとの試行錯誤に時間を取られ，テストを回すところまでたどり着けないからです．

Rust では，次の二つの仕組みでこれが大きく簡単になります．

- **Rust で書かれた依存は `cargo build` が全部面倒を見る．** ダウンロード，ビルド，バージョンの整合性の確認まで自動です．`configure` や CMake の設定は不要です
- **MPI，HDF5，CUDA のような外部ライブラリは「実行時に読み込む」ことができる．** ビルドの時点ではこれらのヘッダやライブラリが不要で，プログラムを実行したときに，その計算機にインストールされているものを探して読み込みます（`dlopen`）．例えば，
  - [rsmpi-rt](https://github.com/tensor4all/rsmpi-rt)：MPI を実行時に読み込む Rust バインディング（tensor4all，実験段階）．ビルド時に C コンパイラや MPI のヘッダが不要です
  - [hdf5-rt](https://github.com/tensor4all/hdf5-rt)：HDF5 を実行時に読み込む Rust バインディング（tensor4all）
  - [cudarc](https://github.com/chelsea0x3b/cudarc)：CUDA の Rust バインディング．既定の設定が実行時読み込みで，ビルド時に CUDA ライブラリが不要です
  - [cblas-inject](https://github.com/shinaoka/cblas-inject)：BLAS の実装（OpenBLAS，MKL など）を実行時に差し込む仕組み

実行時読み込みには，次の利点があります．

- **ビルドは誰の計算機でも同じ手順**（`cargo build --release`）で済み，計算機ごとの Makefile の書き換えが不要になる．AI も，手元のノート PC でも CI でも同じ手順でビルドとテストを回せる
- **実行時には，その計算機向けに最適化された MPI や BLAS が使われる**．スーパーコンピュータのベンダー製 MPI も，そのまま使えます
- **Python や Julia から呼んだときに，それらがすでに読み込んでいる MPI や HDF5 を共有できる**（mpi4py，MPI.jl，h5py，HDF5.jl と同じ通信やファイルを扱える）

### 他で開発された高性能なライブラリを再利用しやすい

OpenMX の部品を他人が使うだけでなく，**OpenMX 側も，他で開発された高性能な部品を `cargo add` で取り込めます**．例えば，

- **線形代数：** [faer](https://github.com/sarah-quinones/faer-rs)（Rust だけで書かれた高性能な線形代数ライブラリ，MIT）
- **テンソルの転置・並べ替え（permutation）と縮約：** [strided-rs](https://github.com/tensor4all/strided-rs)，[tenferro-rs](https://github.com/tensor4all/tenferro-rs)（tensor4all，Apache-2.0）
- **スレッド並列：** [rayon](https://crates.io/crates/rayon)（OpenMP の `parallel for` に相当する機能）
- **FFT：** [rustfft](https://crates.io/crates/rustfft)，または FFTW のバインディング

これらは，それぞれの分野の専門家が性能と正しさを磨き続けているライブラリです．第一原理計算コードの開発者が，転置や線形代数の最適化を自前で抱え込む必要はなくなり，物理に集中できます．ライブラリ側の改良（新しい CPU や GPU への対応など）は，バージョンを上げるだけで取り込めます．

なお，これらのライブラリの多くは MIT や Apache-2.0 で公開されており，GPL のコードからも使えます．ここでも，6 節で説明するライセンスの一方通行の関係が効いています．

### 他の言語からも使える

Rust の部品は，C，Fortran，Python，Julia から呼べます．**既存の OpenMX（C）から呼ぶこともできる**ので，部品を一つずつ置き換え，そのたびに元の OpenMX と数値を突き合わせる，という段階的な移行が可能です．

## 5. 部品が外でも使われる：phonopy と libxc に学ぶ

AI 開発のために部品に分けると，副産物として，**部品そのものが他のプロジェクトで使えるようになります**．これがうまくいった例が，第一原理計算の周辺にすでにあります．

### phonopy は「部品」として広く使われている

[phonopy](https://phonopy.github.io/phonopy/)（東後篤史氏ら）はフォノン計算のためのソフトウェアです．DFT 計算そのものは行わず，力の計算を外部のコードに任せます．その結果，次のように広く使われています．

- **20 近い計算コードとのインタフェース：** VASP，Quantum ESPRESSO，ABINIT，SIESTA，WIEN2k，CP2K，FHI-aims，CASTEP，LAMMPS など（[公式ドキュメント](https://phonopy.github.io/phonopy/)）
- **Python ライブラリとして使える：** コマンドだけでなく API が公開されており，Materials Project のワークフロー基盤 [atomate2](https://github.com/materialsproject/atomate2) などが内部で phonopy を呼び出しています
- **関連プロジェクトの土台：** フォノン間相互作用を扱う phono3py，対称性解析ライブラリ [spglib](https://spglib.readthedocs.io/)（C で書かれ，Python，Fortran，Rust，Ruby から使える）

### phonopy のライセンスの変遷

注目すべきは，phonopy も最初から緩いライセンスだったわけではないことです．公式の変更履歴（[changelog](https://github.com/phonopy/phonopy/blob/main/doc/changelog.md)）によると，

| 時期 | バージョン | ライセンス |
|---|---|---|
| 〜2010 年 | 〜0.9.2 | GPL |
| 2010 年 12 月 | 0.9.3 | LGPL に変更 |
| 2012 年 3 月 | 1.3 | **New BSD に変更**（現在まで） |

phonopy と spglib は現在どちらも BSD-3-Clause です（[phonopy](https://github.com/phonopy/phonopy)，[spglib](https://github.com/spglib/spglib)）．

### もう一つの例：libxc

交換相関汎関数のライブラリ [libxc](https://libxc.gitlab.io/) は MPL-2.0（後述の「弱いコピーレフト」）で公開されており，公式サイトの一部リストだけで **VASP，Quantum ESPRESSO，ABINIT，SIESTA，CP2K，GPAW，PySCF，ORCA など 55 のコード**が利用しています．商用コードも含め，多くのコードが汎関数の実装を共有しています．

### 教訓

成功している部品には共通点があります．

1. **機能が小さく，はっきりしている**（フォノン，対称性，交換相関）
2. **ライブラリとして呼び出せる**（API がある，他言語から使える）
3. **他のコードが依存しやすいライセンスである**（BSD，MPL）

1 と 2 は，AI 開発のためのモジュール化で自然に満たされます．残るのは 3 です．そして，こうした部品は使われるたびに引用されます．

### OpenMX なら：PAO 基底をライブラリにする

OpenMX の最大の特徴の一つは，最適化された擬原子軌道（PAO）基底です．例えば次の機能を一つのライブラリにまとめることが考えられます．

- `.pao`，`.vps` ファイルの読み込み
- 動径関数の補間，球面調和関数との組み合わせ
- 2 中心の重なり積分，運動エネルギー積分（Fourier-Bessel 変換など）
- 規約（位相，軌道の並び順）の明確な定義

これがあれば，

- **機械学習ハミルトニアン（DeepH，HamGNN など）** は OpenMX を改造せずに基底と行列要素を扱える
- **タイトバインディング模型や Wannier 関数の研究**で，OpenMX の基底をそのまま使える
- **他の DFT コード**（新しいコード，GPU 向けのコードなど）が OpenMX の基底を採用できる

そして，そのたびに OpenMX と関連論文が引用されます．

## 6. 残る壁：GPL をやさしく解説

### そもそもライセンスとは

プログラムには著作権があり，書いた人（著作権者）の許可なく複製・改変・配布することはできません．**ライセンスとは，著作権者が「この条件を守れば使ってよい」と示す許可**です．

OpenMX は **GNU GPL バージョン 3（GPLv3）** で公開されています（[OpenMX ダウンロードページ](https://www.openmx-square.org/download.html)）．

### GPL のルールを三つに要約すると

GNU プロジェクトの公式 FAQ（[日本語版](https://www.gnu.org/licenses/gpl-faq.ja.html)）に基づいて要約します．

1. **自由に使い，改変してよい．改変版を自分や組織の中で使うだけなら，公開する義務もない．**
   改変版を「何らかの形で公にする」ときにだけ，ソースコードを GPL で提供する義務が生じます（FAQ [#GPLRequireSourcePostedPublic](https://www.gnu.org/licenses/gpl-faq.ja.html#GPLRequireSourcePostedPublic)）．
2. **改変版や，別の言語への翻訳を配布するときは，GPL で配布しなければならない．**
   FAQ は「著作権法では、作品の翻訳は改変の一種」とし，GPL のプログラムを翻訳したものは同じバージョンの GPL でカバーされなければならないと述べています（[#TranslateCode](https://www.gnu.org/licenses/gpl-faq.ja.html#TranslateCode)）．**C の OpenMX を Rust に移植したものも，これに当たると考えるのが自然です．** AI が書き直した場合も同じです．
3. **GPL のライブラリとリンクして一つのプログラムにしたものを配布するときは，全体が GPL の条件に従う．**
   「GPL のライブラリを使うプログラムは GPL でなければならないか」という問いに，FAQ は「はい」と答え，全体としての作品は GPL でライセンスされなければならないとしています（[#IfLibraryIsGPL](https://www.gnu.org/licenses/gpl-faq.ja.html#IfLibraryIsGPL)）．

### 研究者の日常では何が問題にならず，何が問題になるか

| やりたいこと | GPL で困るか |
|---|---|
| 自分の研究室で OpenMX を改造して計算する | 困らない（配布しなければ義務なし） |
| 改造した OpenMX を GPL で公開する | 困らない |
| GPL の OpenMX 部品を，**自分の GPL のコード**で使って公開する | 困らない |
| GPL の部品を，**BSD や MIT のライブラリ**（phonopy，spglib，多くの Python パッケージ，Rust の crate の大半）の依存に加える | 困る．そのライブラリを使う人全員に GPL の条件が及ぶため，ライブラリの作者は通常それを受け入れない |
| GPL の部品を，**企業との共同研究コードや商用コード**で使う | 困る（ソースを GPL で公開できないため） |
| GPL の部品を，**ライセンスの異なる他の DFT コード**に組み込む | 多くの場合困る |

つまり，GPL は「OpenMX という一つのプログラム」を守るには有効ですが，「**OpenMX の部品を，様々なライブラリやコードに組み込んでもらう**」こととは相性がよくありません．ライブラリの価値は，誰でも気軽に依存できることにあるからです．

参考までに，Rust の公式 API ガイドラインは，crate のライセンスとして「MIT OR Apache-2.0」のデュアルライセンスを推奨しており，その理由を Rust エコシステムとの最大限の互換性としています（[Rust API Guidelines, C-PERMISSIVE](https://rust-lang.github.io/api-guidelines/necessities.html)）．

### 重要：互換性は一方通行

- **BSD，MIT，Apache-2.0 の部品は，GPL の OpenMX からそのまま使えます．** GNU のライセンス一覧でも，これらは GPLv3 と両立するとされています（[license-list: Expat](https://www.gnu.org/licenses/license-list.html#Expat)，[Modified BSD](https://www.gnu.org/licenses/license-list.html#ModifiedBSD)，[Apache 2.0](https://www.gnu.org/licenses/license-list.html#apache2)）．
- 逆に，GPL の部品を BSD や MIT のコードの中で使うと，全体が GPL になります．

したがって，**部品を緩いライセンスで公開しても，OpenMX 本体が GPL であることや，OpenMX の開発の自由は何も損なわれません．**

### 著作権者だけができること

GPL のもとで他人ができないことも，著作権者自身にはできます．

- 著作権者は，同じプログラムを**複数のライセンスで並行して公開できます**（FAQ [#HeardOtherLicense](https://www.gnu.org/licenses/gpl-faq.ja.html#HeardOtherLicense)，[#ReleaseUnderGPLAndNF](https://www.gnu.org/licenses/gpl-faq.ja.html#ReleaseUnderGPLAndNF)）．
- 一方，すでに GPL で公開したものについて，人々が GPL のもとで使う権利を撤回することはできません（FAQ [#CanDeveloperThirdParty](https://www.gnu.org/licenses/gpl-faq.ja.html#CanDeveloperThirdParty)）．

つまり，**OpenMX は今後も GPL のまま存在し続け，それに加えて部品を別のライセンスでも提供する**，という形になります．何かを取り上げるのではなく，選択肢を増やすだけです．

なお，ライセンスを追加できるのは著作権者です．OpenMX に過去にコードを貢献した方々がいる場合，その部分についてはその方々の同意が必要になります．

### 「見ないで書き直せばよいのでは？」

元のコードを見ずに仕様だけから書き直す（クリーンルーム実装）方法もありますが，

- OpenMX の価値は，論文に書かれていない数値的な工夫や規約に多く宿っている
- それを使わずに再実装すると，品質が下がり，元のコードとの一致検証も難しくなる
- どこまでが「改変」に当たるかの判断は難しく，不確実性が残る

何より，それは OpenMX 開発者の皆様の長年の成果を正当に活かす方法ではありません．**著作権者の皆様と一緒に進めることが，唯一まっとうな道だと考えています．**

## 7. 選択肢

Rust では crate ごとに別のライセンスを選べます．「全部 GPL」か「全部 MIT」かの二択ではありません．

### 案 A：新しい Rust の部品を MIT/Apache-2.0 で公開

- OpenMX 本体（C）は GPL のまま
- Rust で作る部品を，著作権者の許諾のもとで Rust 標準の MIT/Apache-2.0 デュアルライセンスで公開
- 最も再利用されやすい（phonopy，spglib と同じ方向）

### 案 B：汎用的な部品から段階的に

- PAO 基底のように，汎用性が高く他分野でも使われる部品から緩いライセンスにする
- O(N) 法や NEGF のような OpenMX 固有の高度な機能は，当面 GPL のままでもよい
- 小さく試して，効果を見てから範囲を決められる

### 案 C：弱いコピーレフト（MPL-2.0）

- MPL-2.0 は**ファイル単位**のコピーレフトです．MPL のファイルを改変した場合はその改変を MPL で公開する必要がありますが，MPL のコードを含まない新しいファイルは別のライセンスにでき，他のコード（商用を含む）と組み合わせることも自由です（[MPL 2.0 FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/) Q1，Q11）
- GPL のコードとも組み合わせられます（[license-list: MPL-2.0](https://www.gnu.org/licenses/license-list.html#MPL-2.0)）
- 「部品の改良は還元してほしい」という GPL の考え方を保ちつつ，ライブラリとしての再利用を妨げない折衷案です．libxc がこの形です

### どの案でも

- 論文の引用やクレジットは，ライセンスではなく README や `CITATION.cff` で明確にお願いできます．phonopy，libxc のように，緩いライセンスでも引用の文化はしっかり機能しています
- なお，モジュール化とユニットテストによる AI 開発そのものは，**GPL のままでも進められます**．ライセンスの判断は，部品を外に届ける段階で必要になるものです

## 8. 想定される懸念について

**「AI が書いたコードを信用できるのか」**
信用の根拠は AI ではなくテストとコンパイラです．各部品に，元の OpenMX から作った正解データとの比較テストを付け，変更のたびに自動で確認します．人間が書いたコードでも，同じ仕組みで品質が保たれます．

**「大域変数をやめると遅くなるのではないか」**
2 節で説明した通り，速度を決めるのはメモリ配置，ライブラリの利用，ノード間のデータ配置などで，いずれも大域変数なしで最適化できます．テストがあれば，最適化そのものも AI に任せやすくなります．

**「企業にただ乗りされるのではないか」**
緩いライセンスでは企業の製品に組み込まれることもあり得ます．ただし，著作権表示の保持は義務です．懸念が大きい部品は GPL のまま残す（案 B）か，改良の還元を求める MPL-2.0（案 C）を選べます．libxc は MPL-2.0 のまま商用コードにも使われ，そのことで存在感を高めています．

**「OpenMX 本体の方針に影響しないか」**
影響しません．OpenMX 本体は従来通りのライセンス・体制で開発を続けられます．部品は GPL の OpenMX からもそのまま使えるので，Rust 側で改良された部品を本体に取り込むこともできます．

## 9. 小さく始める提案

どの段階も，AI エージェントが作業し，人間は設計と物理の判断，結果の確認を担います．

1. 部品を一つ選ぶ（第一候補は PAO 基底と 2 中心積分）
2. その部品の API（関数の形）を一緒に設計する
3. OpenMX にデータ出力のコードを追加し，正解データを作る（AI で自動化できます）
4. AI が Rust で実装し，OpenMX と数値が一致することをユニットテストで自動確認する
5. その部品で，GPU 化などの機能追加を AI に任せ，ファーストフィードバックが実際に回ることを確かめる
6. 合意したライセンスで公開し，DeepH や HamGNN のようなプロジェクトに使ってもらう
